# 社区这座城：city.lizheng.ai 和主页「我们在建一座城」

超线性学院社区的成员地图。每一盏灯是一位成员；两个人之间只要有人给对方的帖子或评论留过言、点过赞，就连上一条线。它出现在两处：单独的页面 city.lizheng.ai，和主页「我们在建一座城」这一段（一扇看得见这座城的窗）。两处用同一份数据、同一套画法；浏览器画不了的时候（没有WebGL2），主页这一段退回一张点阵地图。

## 城里有什么

- **斜着看的一座城**：城是平的，像从飞机上斜着看一座夜里的城市：圆盘总是带一点倾斜（宽屏斜一些，竖着的手机屏正一些，但从不正对着看），所以不会被看成一个可以转的球。拽它就转：看全城时用手指或鼠标横着拖，城跟着转，靠近你的一侧跟着手走，松手还会惯性转一会儿；放大之后或看一个人时，拖动是移动地图。主页的窗也是斜着的，横着拖能转，竖着滑照常滚动页面。2026-10-11立正觉得正圆像一个三维的球，想拽着转；考虑过做成真的三维球，没做：球的背面永远看不见，两万多人总有一半藏在后面，「越靠中间来得越早」的年轮也没了。
- **位置**：越靠中间的人加入得越早，一圈一圈往外长，像年轮，也像城市的一环、二环、三环。每个人占的面积一样大，所以灯是均匀铺开的；某个月加入的人多，那一圈就厚。同一段时间加入的人里，来往多的人排在相近的方向（布局见下）。
- **三种线**：点赞之交（只有点赞）、聊过几句（至少一条评论或回复）、常来常往（双方都给对方留过言，并且评论不少于4条，或者跨了3个月以上；也包括双方都有来往、互动很多又跨月的）。前两种是暖白色，越常来往越亮；常来常往是薄荷绿。
- **团队的线**：管理员和版主（2026年10月有16个账号，含立正、鸭哥和官方号）几乎和所有人都有来往，他们的线全画出来会在中心汇成一片白。所以总览时不画团队的线，只画成员之间的；指到或点开团队成员时，他们的线才亮。
- **一个人的卡片**：指到一盏灯，浮出TA的卡片：名字、哪年哪月加入、发了几个帖子、几条评论、和多少人有来往（是0的那项不显示）。城和主页的窗用同一套内容。
- **动起来的地方**：没人操作时整座城慢慢转；最近两个月有过评论的连线上偶尔有光点流过。系统设置「减少动态效果」时，不播开场、不转、不流动。

## 页面 city.lizheng.ai

- **开场**：从2024年8月开始，一个月一个月重放这座城长起来的过程，镜头跟着往外拉。点一下或拖动就跳到现在。底部时间轴可以拖到任何一个月，或者重播；时间轴上方是那个月和到那时为止的成员数、连接数，开场时跟着城一起往上涨，停在今天就是每天更新的总数。
- **版面**：城是视觉中心，四周只留必要的字：左上是标题和一句说明，右上（手机上是标题下面）是搜索，底部是时间轴、数字、图例和加入按钮。成员数和连接数原来在顶上，2026-10-11立正要求挪到下面（和时间轴上的数字本来就重复），标题也调小了一点。
- **看一个人**：点一盏灯（或搜名字、随机遇见一位），其他线退暗，这个人的线全亮，光点沿着TA的线流向TA，镜头把TA和来往对象框在空出的地方。面板顶上是TA的卡片，下面紧跟「打开TA的主页 ↗」和「复制这张图的链接」，再往下是TA各种来往的比例和来往最多的人：各是哪种来往、评论和点赞次数、从哪个月开始。点名单里的人可以接着走下去。网址变成 `#<public_uid>`，复制下来发给别人，打开就是这个人；浏览器的后退会回到上一个人。
- **手机上的面板**（`sheet.ts`）：从底部升起，平时只露出卡片那一截（名字、数字、主页链接），城占屏幕的大半；往上拖或点一下把手、卡片，展开成几乎整屏的名单；往下拖回到卡片那一截，再往下拖或一甩就关掉。点名单里的人，面板落回卡片那一截，好看清新的人的线。看一个人时，页面顶上只留一行「超线性学院 · Superlinear Academy」，大标题收起来，不压住人和线。
- **搜名字**（`find.ts`，城和主页的窗共用）：名字开头对上的排在包含的前面，有来往的人排在没来往的前面，同一组里来往多的在前，所以搜「鸭」先出来的是真正的鸭哥，而不是一个叫「鸭哥」但从没互动过的账号。
- **头像**：放大到一定程度，或点开一个人时，连接最多的人显示头像和名字；没有头像的人只显示名字。头像和名字作为一个整体摆放，不压页面文字，也不互相重叠，放不下的人只保留一盏灯，指上去能看到是谁。
- **手机上的手势**：总览时灯挨得太近，手指点不准，所以点城里一下是放大到那里，放大到能分清每盏灯之后，点灯或名字才是看这个人；右下角有一排放大、缩小和「全城」按钮（在城下面、椭圆空出来的角上，原来在屏幕右侧中间，会挡住城），看一个人时它们在底部面板正上方，按它们以这个人为中心缩放，名字和镜头都让开按钮。拖动、捏合有边界，拖出城外会弹回来。
- **浏览器自己不缩放页面**：页面就是地图，所以关掉了浏览器对整页的缩放：连点两下按钮不会被当成双击放大（`touch-action: manipulation`），捏合只缩放城（视口 `maximum-scale=1`，iPhone 的 Safari 不认它，另外拦了 `gesturestart`），搜索框在触屏上是16px（小于16px时 Safari 点进去会把整页放大）。2026-10-11立正在手机上连点加号，整页被放大、卡片看不见，由此修的。主页这一段的搜索框同样是16px，整段也关掉了双击放大。
- **横着拿手机**（宽于760、高不过560像素）：用宽屏的排法但少放字：不显示导语、图例和说明，面板占满右侧整列；看一个人时大标题和搜索收起来。

## 主页这一段

**窗**（`CityWindow.tsx` + `embed.ts`）：同一份数据、同一套画法，斜着看让圆盘铺满宽框，慢慢转；第一次滚到时灯从中心亮起。指到一盏灯，亮出这个人的线、绿圈和TA的卡片，框角浮出「进入这座城 ↗」。点一下（手机上点一下）卡片就停住、城也不转了，卡片下面是两条路：「打开TA的主页 ↗」（新窗口开 Circle 主页）和「看TA和谁连着 →」（进入 city.lizheng.ai 并停在这个人）；点空白处、按 Esc 或点 × 关掉。按名字找成员和随机遇见一位也是在窗里打开这个人的卡片，不直接跳走。卡片总放在灯的上方或下方、不出框；为了放得下，手机上这扇窗高360像素。只在这一段接近屏幕时加载、在屏幕上时才画。

**退路：点阵**（`CityField.tsx`）：浏览器画不了这座城（没有WebGL2）或关系图数据没加载出来时显示。每个点是一位成员，按发帖和评论排序，最活跃的人在中心、最亮；指到点上看名字、加入月份、帖子和评论数，点开是TA的 Circle 主页（手机上先点出卡片，再点卡片打开）；上方可以按名字找人、随机遇见一位。第一次进入视线时灯从中心向外亮起，之后有一道缓慢的明暗波、一束跟着鼠标的柔光和零星闪烁的窗灯；减少动态效果时静止。数据到达前说明文字和搜索栏先占好位置，下面的内容不跳动。

## 数据从哪里来

- **成员**：Circle Admin API 的成员列表（`community_members`）。Circle 按加入时间从新到旧返回，所以每天只读开头一页就能补上新成员（通常1次请求）；全量（约255次请求）大约每周读一次，名单和 Circle 的人数对不上（有人离开）时也会提前全量重读。名单在 GitHub Actions 的缓存里跨天保留（只有名字、主页id、头像地址、帖子评论数、加入和最近访问时间，没有邮箱）；缓存丢了就全量读一次。名字像邮箱或电话号码时留空。
- **来往**：Circle Data API 的事件流（`community_events`）里的三种事件：`post.liked`（给帖子点赞）、`post.comment.liked`（给评论点赞）、`post.comment.created`（评论或回复）。评论连到帖子作者，回复连到被回复的那条评论的作者，点赞连到被点赞的帖子或评论的作者。
- **不算的**：给自己帖子或评论的互动、已经不是成员的人、私信、群聊和直播聊天。Data API 不能按事件类型筛选，每次读取会收到所有事件（大部分是加入和离开空间），脚本只留下这三种，读取时就丢掉名字、邮箱和正文。
- Data API 和 Admin API 是两套额度：Data API 每分钟600次、每次2,000条事件，不占 Admin API 的月度额度。2026年10月从头读完全部历史约850次请求、在 GitHub 上约11分钟；每天的任务都从头读（互动明细不放进 GitHub 的缓存），本地缓存（`tmp/community-graph/interactions.ndjson`）则只读新增的部分。Admin API 的成员列表没有互动，Data API 的事件没有名字和主页id，所以两个都要读。
- **花费**：不花钱。Circle 套餐已含两个接口；Vercel Blob 上是 graph.json（约1.5MB，压缩传输约400KB）、city.json（约0.75MB，压缩约210KB）和一张约0.85MB的头像图。

## 怎么更新

- GitHub Actions 每天北京时间10:00（`.github/workflows/community-city.yml`）跑一次 `pnpm community:graph --upload`：读一遍 Circle，写出 graph.json、city.json 和头像图，传到 Vercel Blob（`lizheng-community`），再把线上文件读回来核对。页面在浏览器里读 Blob 上的文件，所以不需要重新部署。也可以在 Actions 页面手动运行。
- 需要的密钥：`CIRCLE_ADMIN_API`、`CIRCLE_DATA_API`、`BLOB_READ_WRITE_TOKEN`，都放在 GitHub 仓库的 Actions secret 里；本地放在 `.env`（`BLOB_READ_WRITE_TOKEN` 在 Vercel 上是敏感变量，拉不下来，所以上传一般交给工作流）。工作流日志只打印数量，不打印名字。
- 中途失败不会覆盖线上数据：成员读回来不到总数的98%时不写文件；新数据的人数或连接数比线上少10%以上时不上传（确认无误加 `--force`）。
- 头像图内容变了就换新文件名，页面缓存不会把新数据配上旧头像；上传后只留新的和上一张（一小时内打开过页面的人可能还在用），更早的删掉。

## Circle Admin API 预算

- Admin API 的月度额度和其他超线性工具共用。规则在 `superlinear/1-会员社区/circle-data-analytics` 的 `docs/data-refresh-and-measurement.md`：先预留最坏请求数，默认2,400次硬停止，并保留至少600次应急空间。这里每天通常1次请求补新成员，大约每周全量约255次，一个月约1,100次。
- `--max-admin-requests`（工作流用300）是硬上限：全量读需要更多请求时（成员超过30,000人）脚本不会开始，需要先调高预算。

## 手动运行

```bash
pnpm community:graph --fetch-only
pnpm community:graph
pnpm community:graph --upload
```

第一条只更新本地缓存；第二条在 `client/public/community/` 写出 graph.json、city.json 和头像图（开发服务器读的就是它们）；第三条同时上传。没有 Circle 的密钥时用缓存里的成员名单，加 `--skip-events` 也不读新的互动，可以离线重建文件。第一次在一台新电脑上跑，可以加 `--seed=…/circle-data-analytics/private/events-part1.ndjson,…/events-part2.ndjson`，先从已有的导出里导入历史，只向 Circle 读之后的部分。成员名单一周全量读一次，`--refresh-members` 现在就全量重读。`--no-avatars` 不做头像图。

本地看页面：`pnpm dev`，打开 `/community-app/`；英文版加 `?lang=en`。

## 数据格式

**graph.json**（`scripts/community/output.ts`）：城和窗读它。成员按加入时间排序，所以第 i 位成员的半径就是 √((i+0.5)/总人数)，方向是 `angle[i]`（0–9999 表示一整圈）。连接按两端序号排序，`a` 存和上一条的差值。

```json
{ "version": 1, "generatedAt": "2026-10-11", "start": "2024-08", "months": 27, "count": 25317,
  "linked": [...], "names": [...], "joined": [...], "angle": [...], "heat": "…",
  "activity": [序号差, 帖子数, 评论数, …], "staff": [...],
  "pairs": { "a": [...], "b": [...], "tie": "1213…", "likes": [...], "comments": [...], "first": [...], "last": [...] },
  "avatars": { "file": "avatars-xxxxxxxxxx.webp", "columns": 32, "rows": 32, "cell": 64, "cells": [序号差, 格子, …] } }
```

`joined`、`first`、`last` 是从2024年8月起的月份序号。头像图只收连接最多的1,024位有头像的成员（64×64像素一格）。

**city.json**（`scripts/community/city.ts`）：点阵读它。成员按活跃度从高到低排序。

```json
{ "version": 1, "generatedAt": "2026-10-11", "count": 25317, "heat": "9987…000", "linked": [...], "names": [...], "joined": [202303, …], "posts": [12, …], "comments": [48, …] }
```

`joined` 是加入月份（YYYYMM，未知为0）；`posts`、`comments` 在最后一位有帖子或评论的成员处结束，之后的成员都是0。

两个文件里的 `heat` 是同一个定义（`memberHeat`）：活跃度 = 帖子数×3 + 评论数，有发帖或评论的成员为3–9（分档：1、3、10、30、100、300、1000）；没有的成员按最近一次访问给0–2（30天内为2，180天内为1）。

## 布局

`ringLayout`（`scripts/community/graph.ts`）：每个人的半径由加入顺序决定；方向先按向日葵螺旋均匀撒开，再迭代40轮：每个人朝自己来往对象的方向靠（常来常往拉得最重，团队的线不参与），然后每120个同期加入的人重新均匀摊开一整圈，只保留谁挨着谁。只靠拉的话所有有来往的人会挤到同一边；每轮重新摊开，保持密度均匀。

## 页面怎么放在 city.lizheng.ai

和 ask.lizheng.ai 一样由主站托管：`client/community-app/` 是 Vite 的第二个入口，构建到 `dist/public/community-app/`；`scripts/prerender-community.ts` 写出英文页 `/community-app/en/`。`vercel.json` 里 `city.lizheng.ai` 的 `/` 和 `/en` 指向这两页，`community.lizheng.ai`（旧名，整站308跳转，旧链接包括 `#某人` 照常能用）和 `www.lizheng.ai/community-app` 都跳到 city.lizheng.ai。两个子域名都加在 Vercel 项目 `lizheng-personal-site_codex` 里（lizheng.ai 的解析在 Vercel，加域名时会自动加记录）。仓库里的目录、脚本和数据路径仍叫 community（`client/community-app/`、`pnpm community:graph`、Blob 的 `community/`），只有对外的地址改了。

## 需要立刻把某个人拿掉

把线上 `graph.json` 里对应的 `linked` 和 `names` 改成空字符串、从 `avatars.cells` 去掉TA，`city.json` 里对应的 `linked` 和 `names` 也改成空字符串，再用 `vercel blob put` 覆盖同一路径，不需要调用 Circle API。TA的灯和线还在，但不再显示名字、头像和主页链接。第二天的定时任务会照 Circle 重新生成这两个文件，所以要长期隐去某人，还得在生成时跳过TA（目前没有这样的名单，真有人提出时再加）。
